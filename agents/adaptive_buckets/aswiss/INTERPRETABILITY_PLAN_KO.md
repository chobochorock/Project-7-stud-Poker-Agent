# ASWISS 해석 도구 계획 (2026-11-06, 계획만, 구현 전)

**목표:** 실제로 표본으로 뽑은 상황 하나를 사람이 읽을 수 있게 풀어낸다. 그 상황이 어느 bucket에 속하는지, 그 bucket이 어떤 전략을 쓰는지, 어느 bucket에서 갈라져 나왔는지, 왜 갈라졌는지를 보여 준다. 모든 bucket과 전략을 훑어볼 수 있는 웹 페이지로 만든다.

## 지금 있는 것과 없는 것 (7-stud `history` 분할 기준)

| 항목 | 상태 |
|---|---|
| 상황 → bucket | 있음. 키 = street, 합법 행동 + 내 직전 결정의 bucket과 행동 + 그 뒤 상대 행동 + 카드 군집. 평가기와 같은 조회로 구한다 |
| bucket의 전략 | 있음. 평균 정책, 현재 정책 |
| 가계도 | 있음. bucket마다 부모 번호가 스냅숏에 저장되고, 은퇴한 부모도 남는다 |
| 카드 군집의 뜻 | 계산할 수 있음. atlas 군집은 18차원(쇼다운 족보 9종 확률, 평균 순위, 양쪽 공개 카드 특징) 위의 k-means다 |
| 분기 이유 | **없음**. 분할 라벨(구성원의 regret이 유의하게 가리킨 행동), z값, 표본 수, epoch를 저장하지 않는다. 판정 창은 epoch마다 지워져서 나중에 복원할 수 없다 |

- 원본 저장은 지금의 이진 스냅숏·checkpoint를 그대로 둔다. 학습과 조회에는 이쪽이 훨씬 효율적이다.
- 아래의 SQL과 웹 페이지는 스냅숏에서 필요할 때 만드는 분석용 사본이다.

## 1. 분할 기록 (학습기, 가장 먼저)

- 분할마다 한 줄씩 `OUT/splits.csv`에 남긴다.
  - 열: epoch, roots, 종류(앞 방향/역방향), 부모 bucket, 자식 bucket, 라벨, 옮겨 간 키 수, 라벨 행동의 표본 수·누적 regret·z값(= R/√Q)
  - 라벨은 창 라벨과 평균 라벨의 조합 코드를 행동 이름으로 풀어 적는다. 라벨이 "없음"이면 그렇게 적는다.
- 학습 결과는 바뀌지 않아야 한다. 켜고 끈 실행의 스냅숏이 바이트 단위로 같은지 확인한다.
- 재개할 때는 checkpoint 이후의 행을 잘라 낸다(`backward.csv`와 같은 방식).
- **시점:** 분기 이유는 이 코드로 시작한 실행에만 생긴다. 노트북의 다음 긴 실행 전에 넣는다. 그 전 실행은 가계도, 정책, 키, 카드 군집까지만 해석할 수 있다.

## 2. 내보내기 (스냅숏 → CSV → SQLite)

- 명령: `aswiss_stud export --snapshot S --atlas A [--splits OUT/splits.csv] [--hands N --seed X] [--street 5|6|7] [--live-only]`. CSV를 쓴다.
- `to_sqlite.py`: CSV를 SQLite 파일로 옮기고 색인을 만든다(파이썬 표준 라이브러리 `sqlite3`, 추가 설치 없음).

| 표 | 내용 |
|---|---|
| `buckets` | id, 부모 id, street, 합법 행동, 생긴 epoch, 분기 라벨, 깊이, 살아 있는지, 평균·현재 정책(행동별 열) |
| `keys` | street, 합법 행동, 직전 bucket, 직전 행동, 상대 행동열(글자), 카드 군집 → bucket |
| `clusters` | street, 군집 번호, 표본으로 구한 군집 평균(족보별 확률 등), 한 줄 설명(예: "투페어 이상 60%, 상대 K 페어 노출") |
| `splits` | 1번의 기록 그대로 |
| `decisions` | 표본 핸드 N개의 결정마다: 핸드 번호, 좌석, street, 내 카드, 보이는 카드, 베팅 이력, 키, bucket, 그 시점 정책 |

- 가계도는 `WITH RECURSIVE` 질의로 뿌리(맥락별 첫 bucket)까지 거슬러 올라간다.
- 크기 추정: 1억 roots `hist_bbf`(bucket 기록 약 306만 개)는 1–3GB다. street별, 살아 있는 bucket만 고르는 일부 내보내기를 둔다.
- 검증:
  - SQL에서 읽은 정책이 표본 결정마다 `Model::strategy`와 같아야 한다.
  - SQL 가계도가 `hresolve`와 같은 bucket에 닿아야 한다.

## 3. 웹 페이지 (bucket 탐색기)

- 로컬 서버로 띄운다(파이썬 표준 라이브러리 `http.server` + `sqlite3`, 추가 설치 없음). 수백만 bucket이라 정적 페이지 하나에 다 넣지 않고 서버가 페이지 단위로 질의한다.
- 화면 구성:
  1. **목록:** 모든 bucket. street, 합법 행동, 카드 군집, 정책 범위(예: 베팅 확률 > 50%), 분기 라벨, 깊이로 거르고 정렬한다. 페이지 단위로 넘긴다.
  2. **bucket 상세:**
     - 키 목록(글자로)
     - 평균·현재 정책 막대
     - 방문 수
     - 조상 사슬: 각 단계의 분기 라벨, z값, 정책 변화
     - 자식 목록
  3. **상황 해석:** 표본 핸드 하나(`decisions` 표) 또는 직접 넣은 카드·행동을 결정마다 한 줄씩 풀어낸다. 직접 넣은 입력은 C++ `explain` 명령을 불러 군집과 키를 구한다. 예:
     > "6구, 상대가 하프 레이즈를 함. 당신은 5구에 bucket B812에서 콜했음. 카드는 군집 523(투페어 이상 58%, 상대 K 페어 노출). → bucket B40,211. 이 bucket은 epoch 9에 B13,077에서 갈라졌다: 구성원의 CALL regret이 유의(z=3.1, 표본 2,104). 평균 정책은 콜 64%, 폴드 21%, 레이즈 15%."
  4. **(선택) 비교:** 같은 상황에서 k-means 스냅숏이나 다른 epoch 스냅숏의 정책을 함께 본다.
- 질의 예시도 페이지에 둔다. 예: "약한 카드 군집인데 베팅 확률이 높은 bucket" = 블러프 후보, "강한 군집인데 체크·콜 위주" = 슬로플레이 후보.

## 4. 해석의 한계 (페이지와 논문에 적을 것)

- 분기 이유의 근거는 표본 반사실 regret이다. "그 행동을 했다면 표본상 얼마나 더 벌었나"이지, 사람식 이유가 아니다. 블러프·밸류 같은 말은 정책, 카드 군집, 베팅 이력을 묶어 붙이는 해석이다.
- 카드 군집은 휴리스틱 atlas(k-means)라, 군집 설명은 평균값 요약이다.
- 원 정보집합이 아니라 bucket 단위 전략이다. 같은 bucket 안의 상황들은 같은 정책을 쓴다(그것이 추상화다).

## 5. mini-stud 판

- 정보집합 키가 이미 읽을 수 있는 문자열이고(`p0|hQKA|dQ|rK|oA|s0:K/A|b...`), 정보집합이 5만 개라 모두 나열할 수 있다.
- 같은 표 구조로 먼저 만들어 도구를 검증하는 데 쓴다.

## 6. 쓸모에 대한 메모

- 신경망 비교군(MMD, ESCHER, ReBeL)에는 이런 구조가 없다. k-means에는 카드 군집만 있다. "근거를 보여 주는 전략"은 ASWISS의 부수적 장점으로 논문에 쓸 만하다.
- 판매 아이디어(인공지능 전략)로 보면 학습·복기 도구 쪽이 맞다. 실제 돈이 걸린 대국에서 쓰는 봇은 대부분 플랫폼 약관 위반이다.
